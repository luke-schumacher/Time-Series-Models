Where we are

Two of the three models are good enough to ship. The third — the one that predicts how long a scan takes — is a very expensive lookup table, and that is the whole story of the last two months.

What works

The patient-handover model is the win column. Its event mix matches real scanners almost exactly, and the day-level volume is right: synthetic visits contain 7.9 scans on average against a real 8.6, with an identical median of 8. Scan lengths are the right order of magnitude, aborted scans appear at roughly the right rate (3.0% against a real 3.6%), and the whole pipeline runs end to end without hand-holding.

What does not

Three things, in order of how much they matter:

  • The duration model ignores every input except the protocol name — and the protocol name is the one input it is not allowed to use. It is beaten on held-out data by a spreadsheet.
  • Anatomy collapses. Real scanners cover 56 body parts; we generate 7. Eight of the fifteen real body groups are never produced at all.
  • Scans run too long and visits have no pauses. 4.5% of generated scans exceed ten minutes; in real data it is 0.06%. Downstream, the day is over-filled and the simulator throws away patients it had already scheduled.

The single next move

Stop adding features to the duration model. Change what it is asked to predict: train it on the residual against the protocol average, or remove the protocol input entirely and score against it. The evidence that this will work is in §5 — fitted as a plain table on the same rows, the sequence parameters reach 9.7 s of error against the protocol benchmark's 13.2 s. The signal is in the data. The network is not using it.

Before you ship the next Qlik bundle

The 40 CSVs in ~/Downloads/Results 31082026 are two generator fixes behind the code. Measured on those files: 100% of the gaps between scans inside a visit are exactly 0 s (commit c9e8604 put that pause back), and the protocol column carries the old eight-name placeholder pool (t1_mprage, t2_flair, …) rather than sampled real protocol names. Their per-scanner row counts do not match the step-07 log from the latest run either — 3,793 rows for scanner 183242 here against 3,574 in the log.

They are perfectly usable for the anatomy and event-mix charts. Re-run step 07 on current main and re-download before using them to judge timing.

02How it is
built

Architecture

Real scanner event logs go in at the top; a month of invented-but-plausible scanner activity comes out at the bottom, in exactly the same CSV shape. That shape-match is deliberate: it is what lets the Qlik dashboard put real and synthetic side by side without a single column rename.

The pipeline, top to bottom
Numbered boxes are Databricks notebooks. Teal = real data, orange = generated.
All three models are the same transformer: 128-dimensional, 4 attention heads, 3 encoder and 3 decoder layers, 512-wide feed-forward, with a log-space duration head. Small on purpose — the training set is tens of thousands of sequences, not millions.

Two pipelines, and why

The repository carries the pipeline twice. csv_pipeline/ is the original and owns the exchange and orchestration checkpoints plus the real-data extracts the dashboard compares against. csv_pipeline_seqparams/ is a fork that adds 341 MRI sequence parameters — repetition time, slice count, field of view and so on, read out of the MRI_SUT_1005 message — to the examination model's conditioning. It was forked rather than modified so a failed experiment could not take the working checkpoints down with it. That decision paid off; see §4.

Why the protocol name is not allowed to be an input

This is the constraint that everything else follows from, set with Görtler on 31 July 2026. A protocol is a saved state — one sequence plus roughly fifty parameter settings. Customers keep their own protocol trees, copy Siemens presets, rename them in any language, and edit them; copying destroys the link to the original preset. The result is around 3.8 million protocol names across 15,000 customers against only 3,800 Siemens presets. A model keyed on the protocol name learns one site and transfers to none. So the name stays in the data as a label and becomes the benchmark to beat — never a feature.

04Where it
fails

Four failures, named

Each one below has been reproduced and root-caused, not guessed at. The identifiers F1–F4 are referenced again in the ranked next steps in §6.

F1

The duration model ignores every input except the protocol name

Blocking
What we see

Shuffle any one input and measure how far the prediction moves. Of 346 conditioning features, exactly two move it: the protocol name and the coarse scan type. The other 344 — every one of the 341 MRI sequence parameters, plus the body region and the scanner's own identity — move it by less than 0.05 s, which is indistinguishable from re-seeding the random number generator.

What that costs

Held-out error is 19.1 s. A plain lookup table holding the average duration per protocol name scores 16.2 s on the same data. A 2.1-million-parameter transformer is losing to a spreadsheet — and it is losing while leaning on the one input it is not allowed to use in production.

Why it is not a wiring bug

That was the first hypothesis and it was tested and rejected. The path that carries the conditioning into the duration head exists in the checkpoint and was trained — its weight norm is 1.16, against 1.07 for the scan-type path that demonstrably works. The channel is live and still dead.

The likely mechanism is credit assignment, not capacity. A direct 1,620-row protocol lookup already explains 76% of held-out variance, so it is the cheapest way to reduce the loss, and the gradient reaching the 351-dimensional parameter path dies in the first few epochs. Retraining the same objective will not fix this.

Why it is worth fixing rather than abandoning

The signal is provably present. Fitted as an ordinary table on the same rows, the 89 admissible sequence parameters reach 9.7 s of error against the protocol benchmark's 13.2 s. That clears the ±15 s target Görtler named, beats the benchmark, and uses nothing customer-specific. Roughly eight seconds of accuracy is sitting in the data and the network is not touching it.

F2

Anatomy collapses to seven categories

Major
What we see

Real scanners in this window cover 15 body groups and 56 body parts. We generate 7 and 7. UNKNOWN takes 19.5% of generated scans against 2.2% of real ones, and HEAD is over-produced at 40.5% against 25.5%. Knee (6.2% of real work), shoulder, breast, heart, hip, chest, other and whole-body are never generated at all.

Root cause, in two parts

The vocabulary is too small. The eleven-value body-region list in config.py has no knee and no heart, so step 03 folds brain, liver, knee, lumbar spine, prostate, shoulder and breast into UNKNOWN before training ever sees them.

The source field is empty. BodyPartExamined is null on nearly every exam row. Step 03 tries three guessed key names out of the workflow map and none of them is the real one. It now prints the keys that are actually present, so the next Spark run names the field and the fix is one line.

F3

Scans run long, and the day silently loses patients

Major
What we see

4.54% of generated scans exceed ten minutes; real data has 0.06%. The 99th percentile is 1,205 s against 392 s, and the longest generated scan runs 66 minutes against a real maximum of 19.

The downstream cost, which is the real problem

The day simulator caps a scanner's day at 13 hours. Because generated scans are too long, that cap binds. In the most recent run it bound on 16 of the 20 scanners and discarded 969 patients — 13% of everything the orchestration model had scheduled — plus 938 individual scans. One scanner hit the cap on all 20 working days. Those patients do not appear in the output and nothing downstream knows they existed.

The pause inside a visit

A real visit is 15.1 minutes of scanning inside 22.7 minutes of elapsed time — a third of it is the operator repositioning, talking to the patient, changing coils. The generator advanced the clock by the scan duration alone, so the next scan started the instant the previous one ended. Commit c9e8604 puts the pause back and the newest run reports 15–27% dead time against a real 30.4%. The CSVs currently on disk predate that commit — measured, 100% of their intra-visit gaps are exactly zero.

F4

Patient handovers lose their long tail

Minor
What we see

The mean handover block is 520 s against a real 1,108 s, while the medians sit close together (381 s against 455 s). The model reproduces the typical handover and misses the rare very long one — a shift change, a lunch break, an equipment problem. The event mix itself is correct, which is why this is cosmetic rather than structural.

05The decisive
experiment

One run settles F1

Do not add more features. Three attempts in a row added inputs — TR, slice count, then all 341 parameters — and the permutation result did not move once. The input is not the problem. The target is.

The duration head has a shortcut: predict the protocol's average and stop. Remove that shortcut from what it is asked to predict, and the parameters become the only route left.

Two forms, pick one

  1. Residual training. Subtract the protocol mean from the target, so the head learns only the part the operator changed — which is exactly the part the executed parameters describe. Add the mean back at generation time.
  2. Full ablation. Build the model with no protocol tensors at all (num_protocols=None) and score it against the protocol oracle. Cleaner to interpret, and it is the configuration that would actually ship.

The bar to clear

Held-out error below 16.2 s with the protocol name removed from the inputs. Beating the previous checkpoint is not sufficient and never has been: a model can ignore a new input entirely and still look improved, which is precisely what happened when TR and slice count were added. The tabular fit says 9.7 s is reachable.

The diagnostics are already written

05_feature_analysis.py prints the permutation ranking and 06_compare_models.py prints the conditioning-path weight norm and branches on it — trained-but-dead means an objective problem, zero-initialised means a wiring problem. You do not need another exploratory cycle to know which branch you are in; one training run plus those two notebooks gives the answer.

Why Görtler's argument makes this worth doing

If protocols ran exactly as saved, scan durations would vary by about a second. They vary by fifteen because the operator adjusts after loading — pushing slice count from 15 to 17 once the localiser shows the coverage, or dropping slices when a low-weight patient triggers a specific-absorption-rate limit. The protocol name is the label from before those adjustments. The parameters are what actually ran. Executed parameters should therefore beat the name, not merely match it — and our own data confirms the premise: within a single scanner-and-protocol group, slice thickness varies on 80.5% of scans and repetition time on 56.7%. The message records what ran, not what was saved.

Five traps, each of which has cost a full day

  • Push before you run. The notebooks clone origin/main from GitHub. Uncommitted local work simply does not exist to Databricks.
  • Never %run steps 01 or 02 from another notebook. They begin with %pip install, which restarts the Python process and wipes the caller's state. It surfaces later as a misleading NameError in unrelated code.
  • Databricks caches modules in a live kernel. Correct files on disk do not mean correct code running. Step 04 purges sys.modules; if you add a notebook, purge too, or call dbutils.library.restartPython(). Three consecutive retrains produced byte-identical losses before this was found.
  • Serving code takes its architecture from the checkpoint, never from config.py. Read MODEL_MANIFEST.json and protocol_vocab.json. Omitting num_protocols is not an error — the checkpoint's protocol tensors are silently dropped as "unexpected" and every prediction falls back to the rare bucket. That ran unnoticed for three weeks.
  • A scanner with no exam CSV disappears three notebooks later. That is why 21 configured serials produce 20 outputs — 155687 has no rows in the window, so step 03 writes no schedule for it and step 07 generates no days. Step 02 now prints which scanners fell out; read it.

Refreshing the Qlik bundle

Drop the per-scanner CSVs into qlik/data/real/{exchange,exam}/ and qlik/data/synthetic/{exchange,exam}/, stripping the browser's (1) suffix — plain DATA_<serial>.csv is the handover file, the (1) copy is the scan file. Run python consolidate.py, then drag the two files it writes into Qlik and hit reload. No chart edits, ever — the column names are prefixed deterministically so the six chart expressions never change.

The 20 synthetic scanners from the 31 August run are already sorted into place in the repository. The real side is waiting on the fresh 20-scanner extract.

Honest list of what is not done

No protocol-free accuracy number exists

Every error figure quoted anywhere, including the 19.1 s above, comes from a model that can see the protocol name. The number that decides whether this ships has never been measured.

03f has never been run

Written, unit-tested, needs no Spark, answers the join-coverage question in about ten minutes. It has simply never been executed on a cluster.

The shipped CSVs lag the code

Two generator fixes behind: the intra-visit pause and the protocol sampler. Verified by measurement, not assumed.

Uncommitted work in the tree

qlik/README.md and qlik/consolidate.py carry local edits (label normalisation across the two sides), and presentation/web/ is untracked. Deliberate — none of it was mine to commit unreviewed.
